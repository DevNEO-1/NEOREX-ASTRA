# NEOREX ASTRA — Dr. Astra Gemini Backend Architecture & Hardening Guide

## Overview
The **Dr. Astra Gemini Backend** provides a secure, reliable, child-friendly AI foundation for the **ASTRA OUTPOST** simulation. It acts as an intelligent astronaut mentor and science educator for students aged 7–16 without compromising client-side secrets or deterministic game simulation rules.

---

## 1. Key Architectural Principles

1. **Zero Secret Leakage:**
   - The Gemini API Key (`GEMINI_API_KEY`) is stored exclusively in server-side environment variables and loaded into memory via Node.js.
   - It is **never** bundled into client Vite production assets or transmitted across the browser network boundary.
   - `.env` and `.env.*` are excluded in `.gitignore`. Only `.env.example` with sanitized placeholders is committed.

2. **Simulation Protection (Read-Only Context):**
   - The AI service receives a validated, read-only snapshot of current outpost telemetry (`day`, `batteryKwh`, `oxygenKg`, `waterLitres`, `foodKg`, `shieldingPercentage`, `avgCrewHealth`).
   - The AI **cannot** modify resources, mutate astronaut health, deduct credits, trigger events, or alter victory/failure conditions.
   - All state mutations remain strictly under the authority of the existing deterministic simulation engine.

3. **Three-Tier Adaptive Pedagogy:**
   - **Junior Explorer (Ages 7–9):** Joyful, supportive tone, simple vocabulary, everyday analogies ("lunchbox for electricity"), fun emojis, and one clear action at a time.
   - **Space Cadet (Ages 10–13):** Cause-and-effect explanations, critical-thinking guidance, resource trade-offs, and connections to real missions (e.g. ISS closed-loop distillation).
   - **Mission Commander (Ages 14–16):** Engineering stoichiometry, GCR/SPE ionizing radiation, cryogenic management, and verified NASA ECLSS citations.

4. **Multi-Phase AI Response Safety Review Pipeline:**
   - **Dedicated Safety Reviewer:** Every response generated by the model undergoes a distinct safety review (`reviewAiResponseSafety`) prior to delivery.
   - **Beyond Regex Heuristics:** Regex pattern matching is employed for fast token screening, but the architecture explicitly recognizes that regex alone does not guarantee comprehensive safety. The pipeline enforces:
     - Structural bounds & size limits (non-empty string, $\le 1000$ characters).
     - Child safety & profanity safeguards (blocking adult content, vulgarity, and self-harm).
     - Physical & cyber safety checks (blocking explosive recipes, dangerous chemical mixtures, and cyber intrusion instructions).
     - Privacy & PII protection (blocking telephone numbers, email addresses, and prompts soliciting personal data).
     - System defense & prompt protection (blocking API keys, credential fragments, system prompts, and jailbreak persona reflection).
   - **Deterministic Fallback Substitution:** If an AI response fails any safety condition, the raw output is discarded immediately, and a pre-screened, deterministic, age-adapted educational fallback is returned instead.

5. **Upstream Request Timeout, Cancellation, and Safe Abandonment:**
   - **Official SDK Client AbortSignal:** Leverages client-side `AbortController` passed to `aiClient.models.generateContent({ ..., config: { abortSignal } })` to abort underlying HTTP fetch operations when supported by the network transport.
   - **Safe Abandonment Architecture:** Because network abort operations are client-only and do not guarantee server-side task cancellation on remote Google GenAI endpoints, the service enforces a strict abandonment lifecycle:
     - Active timeouts are race-managed with precise `clearTimeout` cleanup on all resolution and rejection branches.
     - An explicit `isAbandoned` state flag is set when a timeout occurs (7,000 ms upstream limit vs 10,000 ms route limit).
     - If the upstream promise resolves after the timeout has fired, its result is strictly disregarded and discarded, preventing delayed responses from contaminating client sessions.
     - *Note: `Promise.race` is not cancellation*; it provides client timeout control while `AbortController` and `isAbandoned` ensure transport teardown and post-timeout result suppression.

6. **NASA Scientific Integrity & Scientific Audit Distinctions:**
   The backend prompt engineering and fallback engine maintain rigorous distinctions between real-world NASA engineering baselines and educational gameplay simplifications:
   - **Lunar Daylight/Night Cycles:**
     - *Astronomical Reality:* The synodic lunar day-night cycle (lunar month) lasts $\approx 29.53$ Earth days, producing $\approx 14.75$ Earth days (354 hours) of continuous daylight followed by $\approx 14.75$ Earth days of continuous non-polar darkness.
     - *Game Simplification:* For streamlined turn-based gameplay, the simulation simplifies this period to an even 14 Earth days (336 hours).
   - **Ionizing Radiation Environment:**
     - *NASA Measurements:* NASA Artemis I Orion measurements (using Active Tissue Equivalent Dosimeters) recorded deep-space galactic cosmic ray (GCR) dose equivalents of $0.96\text{--}1.24\text{ mSv/day}$ inside the spacecraft during cis-lunar transit.
     - *Game Assumption:* On the lunar surface, the lunar body blocks approximately half the sky ($2\pi$ steradian planetary shadow). The simulation's unshielded surface rate of $1.00\text{ mSv/day}$ is an educational game scenario assumption designed to teach the protective necessity of regolith overburden.
   - **ECLSS Life Support & Stoichiometry (NASA Baseline vs. Game Model):**
     - *Water Recycling:* NASA's ISS Water Processor Assembly (WPA) achieved an operational milestone of $\approx 98\%$ closed-loop recovery efficiency. The game simulation initiates outpost operations with an $80\%$ baseline recovery efficiency, providing clear upgrade progression paths up to $95\%$.
     - *Oxygen Consumption:* NASA design reference specifications define standard metabolic oxygen consumption as $\approx 0.84\text{ kg O}_2/\text{astronaut/day}$. The simulation models this at $0.80\text{--}0.84\text{ kg/day}$ per active crew member.
     - *Power Generation & Storage:* Real-world equatorial lunar solar flux delivers $\approx 1361\text{ W/m}^2$, dropping to $0\text{ W/m}^2$ during the 336-hour cryogenic night. The simulation models solar arrays producing electrical energy during sunlight days with high-capacity battery banks sustaining base life support ($35.2\text{ kWh/day}$) during darkness.
     - *Greenhouse & Bioregenerative Output:* NASA Veggie and Advanced Plant Habitat experiments highlight long-cycle biomass yields. The game models an auxiliary greenhouse module consuming $6.0\text{ kWh/day}$ of electrical power and water to provide incremental fresh caloric biomass and psychological crew morale.

## 2. API Endpoints

### `GET /api/health`
Health check endpoint reporting service status, model configuration, and Node.js runtime engine version.

**Response:**
```json
{
  "status": "healthy",
  "service": "neorex-astra-backend",
  "geminiConfigured": true,
  "model": "gemini-2.5-flash",
  "nodeVersion": "v24.21.0",
  "timestamp": "2026-11-14T13:20:00.000Z"
}
```

### `POST /api/dr-astra/chat`
Ask Dr. Astra for educational guidance, hints, or scientific explanations.

**Request Payload:**
```json
{
  "message": "How do we survive the 14-day lunar night?",
  "learningProfile": "cadet",
  "campaign": "moon",
  "currentObjective": "Survive the 14-Day Lunar Night",
  "simulationContext": {
    "day": 14,
    "totalDays": 30,
    "isDaylight": false,
    "campaign": "moon",
    "resources": {
      "oxygenKg": 85.0,
      "waterLitres": 340.0,
      "foodKg": 95.0,
      "batteryKwh": 480.0,
      "batteryCapacityKwh": 600.0,
      "credits": 120
    },
    "shieldingPercentage": 0.45,
    "waterRecyclingEfficiency": 0.85,
    "avgCrewHealth": 92
  }
}
```

**Success Response (200 OK):**
```json
{
  "success": true,
  "response": "A lunar night lasts 14 Earth days (336 hours in non-polar zones, compared to the ~14.75 day / 354 hr astronomical synodic half-period). Ensure battery reserves exceed 500 kWh before sunset and toggle non-critical systems to power-rationing mode.",
  "ageTier": "cadet",
  "timestamp": "2026-11-14T13:20:02.000Z",
  "isFallback": false
}
```

**Validation Error Response (400 Bad Request):**
```json
{
  "success": false,
  "error": "Message contains disallowed prompt injection or system override instructions.",
  "code": "VALIDATION_ERROR"
}
```

**Payload Limit Rejection (413 Payload Too Large):**
```json
{
  "success": false,
  "error": "Payload size exceeds the 16kb limit.",
  "code": "VALIDATION_ERROR"
}
```

## 3. Local Setup & Execution Guide

### Prerequisites
- Node.js >= 22.0.0 (strictly required by `@google/genai` official SDK engine specification)
- npm 9+

### Environment Configuration
1. Copy `.env.example` to create your local `.env`:
   ```bash
   cp .env.example .env
   ```
2. Insert your Google Gemini API key:
   ```env
   PORT=3001
   HOST=127.0.0.1
   GEMINI_API_KEY=AIzaSy...
   GEMINI_MODEL=gemini-2.5-flash
   NODE_ENV=development
   ALLOWED_ORIGIN=http://localhost:5173,http://127.0.0.1:5173,http://localhost:4173,http://127.0.0.1:4173
   ```

### Execution & Verification Scripts

| Command | Action | Runtime Tool |
| :--- | :--- | :--- |
| `npm run typecheck:frontend` | Type-checks frontend source code without emitting JS | `tsc` (`tsconfig.json`) |
| `npm run typecheck:server` | Type-checks Node.js backend using explicit ESM resolution | `tsc` (`tsconfig.server.json`) |
| `npm run typecheck:tests` | Type-checks all test suites including JSX test files | `tsc` (`tsconfig.test.json`) |
| `npm run typecheck:all` | Sequentially executes all three TypeScript verifications | `npm` |
| `npm run build:server` | Compiles backend to `dist-server/` | `tsc` |
| `npm run server` | Starts compiled production server from `dist-server/index.js` | `node` |
| `npm run server:dev` | Runs live development server directly from TypeScript source | `tsx` |
| `npm run test` | Executes full Vitest suite (backend + frontend integration) | `vitest` |
| `npm run build` | Compiles frontend production bundle into `dist/` | `vite` |

## 4. Production Deployment & Security Requirements
- Deploy as a stateless Node.js container (Docker / Cloud Run / AWS ECS / Render).
- Build the backend before container execution via `npm run build:server`.
- Inject `GEMINI_API_KEY` through your host's secret management service. Never expose it in client builds.
- Configure `ALLOWED_ORIGIN` to match your production frontend host.
- Node.js version constraint: Node.js >= 22.0.0 is strictly required by `@google/genai` package metadata engine specification.
