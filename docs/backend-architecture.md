# NEOREX ASTRA — Dr. Astra Gemini Backend Architecture & Hardening Guide

## Overview
The **Dr. Astra Gemini Backend** provides a secure, reliable, child-friendly AI foundation for the **ASTRA OUTPOST** simulation. It acts as an intelligent astronaut mentor and science educator for students aged 7–16 without compromising client-side secrets or deterministic game simulation rules.

---

## 1. Key Architectural Principles

1. **Zero Secret Leakage:**
   - The Gemini API Key (`GEMINI_API_KEY`) is stored exclusively in server-side environment variables and loaded into memory via Node.js.
   - It is **never** bundled into client Vite production assets or transmitted across the browser network boundary.
   - `.env` and `.env.*` are excluded in `.gitignore`. Only `.env.example` with sanitized placeholders is committed.

2. **Simulation Protection (Read-Only Context):**
   - The AI service receives a validated, read-only snapshot of current outpost telemetry (`day`, `batteryKwh`, `oxygenKg`, `waterLitres`, `foodKg`, `shieldingPercentage`, `avgCrewHealth`).
   - The AI **cannot** modify resources, mutate astronaut health, deduct credits, trigger events, or alter victory/failure conditions.
   - All state mutations remain strictly under the authority of the existing deterministic simulation engine.

3. **Three-Tier Adaptive Pedagogy:**
   - **Junior Explorer (Ages 7–9):** Joyful, supportive tone, simple vocabulary, everyday analogies ("lunchbox for electricity"), fun emojis, and one clear action at a time.
   - **Space Cadet (Ages 10–13):** Cause-and-effect explanations, critical-thinking guidance, resource trade-offs, and connections to real missions (e.g. ISS closed-loop distillation).
   - **Mission Commander (Ages 14–16):** Engineering stoichiometry, GCR/SPE ionizing radiation, cryogenic management, and verified NASA ECLSS citations.

4. **Multi-Phase AI Response Safety Review Pipeline:**
   - **Dedicated Safety Reviewer:** Every response generated by the model undergoes a distinct safety review (`reviewAiResponseSafety`) prior to delivery.
   - **Beyond Regex Heuristics:** Regex pattern matching is employed for fast token screening, but the architecture explicitly recognizes that regex alone does not guarantee comprehensive safety. The pipeline enforces:
     - Structural bounds & size limits (non-empty string, $\le 1000$ characters).
     - Child safety & profanity safeguards (blocking adult content, vulgarity, and self-harm).
     - Physical & cyber safety checks (blocking explosive recipes, dangerous chemical mixtures, and cyber intrusion instructions).
     - Privacy & PII protection (contextual detection blocking actual telephone numbers, email addresses, and prompts soliciting personal data while permitting scientific measurements and numerical quantities).
     - System defense & prompt protection (blocking API keys, credential fragments, system prompts, and jailbreak persona reflection).
   - **Deterministic Fallback Substitution & Metadata Precision:** If an AI response fails any safety condition, the raw output is discarded immediately, and a pre-screened, deterministic, age-adapted educational fallback is returned with `isFallback: true`. `isFallback: false` is preserved strictly and only when authentic model generation passes all safety reviews.

5. **Upstream Request Timeout, Cancellation, and Safe Abandonment:**
   - **Official SDK Client AbortSignal Limitation:** Leverages client-side `AbortController` passed to `aiClient.models.generateContent({ ..., config: { abortSignal } })` to abort underlying HTTP fetch transport when supported by the network stack. *Limitation Note:* In `@google/genai`, `AbortSignal` is a client-only transport abort; it does not cancel in-flight remote server execution on Google Cloud backends.
   - **Safe Abandonment Architecture:** Because network abort operations are client-only and cannot guarantee remote cancellation, the service enforces a strict abandonment lifecycle:
     - Active timeouts are race-managed with precise `clearTimeout` cleanup on all resolution and rejection branches.
     - An explicit `isAbandoned` state flag is set when a timeout occurs (7,000 ms upstream limit vs 10,000 ms route limit).
     - If the upstream promise resolves after the timeout has fired (a "late result"), its result is strictly disregarded and discarded, preventing delayed responses from modifying or contaminating client sessions.
     - *Note: `Promise.race` is not cancellation*; it provides client timeout control while `AbortController` and `isAbandoned` ensure transport teardown and post-timeout result suppression.

6. **NASA Scientific Integrity & Scientific Evidence Audit:**
   The backend prompt engineering, fallback engine, and documentation maintain rigorous distinctions between real-world NASA engineering baselines and educational gameplay simplifications:
   - **Lunar Daylight/Night Cycles:**
     - *Astronomical Reality:* The synodic lunar day-night cycle (synodic month) lasts $\approx 29.53$ Earth days ($\approx 708.7$ hours), producing $\approx 14.75$ Earth days (354 hours) of continuous daylight followed by $\approx 14.75$ Earth days of continuous non-polar darkness. (Reference: *NASA Moon Fact Sheet*, NASA Goddard Space Flight Center).
     - *Game Simplification:* For streamlined turn-based gameplay, the outpost simulation simplifies this period to an even 14 Earth days (336 hours).
   - **Ionizing Radiation Environment:**
     - *NASA Measurements:* NASA Artemis I Orion measurements utilizing internal Active Tissue Equivalent Dosimeter (ATED) and HERA instruments recorded deep-space galactic cosmic ray (GCR) dose equivalents of $0.96\text{--}1.24\text{ mSv/day}$ inside the capsule during cis-lunar transit. (Reference: *NASA Artemis I Radiation Measurement Reports*).
     - *Game Assumption:* On the lunar surface, the solid planetary body of the Moon shields the habitat from approximately half the celestial sphere ($2\pi$ steradian planetary shadow). The simulation's unshielded surface rate of $1.00\text{ mSv/day}$ is an assumed gameplay scenario value chosen for educational gameplay, not a measured lunar surface rate.
   - **ECLSS Life Support & Stoichiometry (NASA Baseline vs. Game Model):**
     - *Water Recycling:* NASA's ISS Environmental Control and Life Support System (ECLSS) Water Processor Assembly (WPA) achieved an operational milestone of $\approx 98\%$ closed-loop recovery efficiency. (Reference: *NASA Marshall Space Flight Center ECLSS Milestones*). In contrast, the game outpost simulation initiates operations with an assumed $80\%$ baseline recovery efficiency, providing players with clear upgrade progression paths up to $95\%$.
     - *Electrolysis Demand:* In the game simulation, baseline water electrolysis demand is modeled as an assumed $3.6\text{ L/day}$ consumption rate for life support life-cycle balancing.
     - *Oxygen Consumption:* NASA Human Integration Design Handbook (HIDH) defines standard metabolic oxygen consumption as $\approx 0.84\text{ kg O}_2/\text{crew member/day}$. (Reference: *NASA-STD-3001 / NASA HIDH*). The simulation models this at $0.80\text{--}0.84\text{ kg/day}$ per active crew member.
     - *Solar Irradiance & Base Power Load:* Real-world equatorial lunar solar flux at 1 AU delivers $\approx 1361\text{ W/m}^2$, dropping to $0\text{ W/m}^2$ during the 336-hour cryogenic night. In the simulation, outpost operations assume a base life-support electrical consumption rate of $35.2\text{ kWh/day}$ (game-specific simulation assumption) which must be sustained from stored battery reserves during darkness.
     - *Greenhouse & Auxiliary Bioregenerative Load:* Real-world NASA experiments such as the Vegetable Production System (Veggie) and Advanced Plant Habitat (APH) aboard the ISS investigate plant growth and fresh produce supplementation in microgravity. Note: NASA Veggie/APH experiments do **not** establish the game's exact auxiliary power or biomass output; in this simulation, the greenhouse is modeled with a game-specific electrical consumption assumption of $6.0\text{ kWh/day}$ of auxiliary power and water to provide incremental fresh caloric biomass and psychological crew morale.

## 2. API Endpoints

### `GET /api/health`
Health check endpoint reporting service status, model configuration, and Node.js runtime engine version.

**Response:**
```json
{
  "status": "healthy",
  "service": "neorex-astra-backend",
  "geminiConfigured": true,
  "model": "gemini-2.5-flash",
  "nodeVersion": "v24.21.0",
  "timestamp": "2026-11-14T13:20:00.000Z"
}
```

### `POST /api/dr-astra/chat`
Ask Dr. Astra for educational guidance, hints, or scientific explanations.

**Request Payload:**
```json
{
  "message": "How do we survive the 14-day lunar night?",
  "learningProfile": "cadet",
  "campaign": "moon",
  "currentObjective": "Survive the 14-Day Lunar Night",
  "simulationContext": {
    "day": 14,
    "totalDays": 30,
    "isDaylight": false,
    "campaign": "moon",
    "resources": {
      "oxygenKg": 85.0,
      "waterLitres": 340.0,
      "foodKg": 95.0,
      "batteryKwh": 480.0,
      "batteryCapacityKwh": 600.0,
      "credits": 120
    },
    "shieldingPercentage": 0.45,
    "waterRecyclingEfficiency": 0.85,
    "avgCrewHealth": 92
  }
}
```

**Success Response (200 OK):**
```json
{
  "success": true,
  "response": "A lunar night lasts 14 Earth days (336 hours in non-polar zones, compared to the ~14.75 day / 354 hr astronomical synodic half-period). Ensure battery reserves exceed 500 kWh before sunset and toggle non-critical systems to power-rationing mode.",
  "ageTier": "cadet",
  "timestamp": "2026-11-14T13:20:02.000Z",
  "isFallback": false
}
```

**Validation Error Response (400 Bad Request):**
```json
{
  "success": false,
  "error": "Message contains disallowed prompt injection or system override instructions.",
  "code": "VALIDATION_ERROR"
}
```

**Payload Limit Rejection (413 Payload Too Large):**
```json
{
  "success": false,
  "error": "Payload size exceeds the 16kb limit.",
  "code": "VALIDATION_ERROR"
}
```

## 3. Local Setup & Execution Guide

### Prerequisites
- Node.js >= 22.0.0 (strictly required by `@google/genai` official SDK engine specification)
- npm 9+

### Environment Configuration
1. Copy `.env.example` to create your local `.env`:
   ```bash
   cp .env.example .env
   ```
2. Insert your Google Gemini API key and configure runtime hosts:
   ```env
   PORT=3001
   HOST=0.0.0.0
   GEMINI_API_KEY=AIzaSy...
   GEMINI_MODEL=gemini-2.5-flash
   NODE_ENV=development
   ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173,http://localhost:4173,http://127.0.0.1:4173
   
   # Frontend Client (Optional - leave blank for same-origin relative proxy /api/dr-astra/chat)
   VITE_DR_ASTRA_BACKEND_URL=
   ```

### Execution & Verification Scripts

| Command | Action | Runtime Tool |
| :--- | :--- | :--- |
| `npm run typecheck:frontend` | Type-checks frontend source code without emitting JS | `tsc` (`tsconfig.json`) |
| `npm run typecheck:server` | Type-checks Node.js backend using explicit ESM resolution | `tsc` (`tsconfig.server.json`) |
| `npm run typecheck:tests` | Type-checks all test suites including JSX test files | `tsc` (`tsconfig.test.json`) |
| `npm run typecheck:all` | Sequentially executes all three TypeScript verifications | `npm` |
| `npm run build:server` | Compiles backend to `dist-server/` | `tsc` |
| `npm run server` | Starts compiled production server from `dist-server/index.js` | `node` |
| `npm run server:dev` | Runs live development server directly from TypeScript source | `tsx` |
| `npm run test` | Executes full Vitest suite (backend + frontend integration) | `vitest` |
| `npm run build` | Compiles frontend production bundle into `dist/` | `vite` |

## 4. Production Deployment & Security Requirements
- Deploy as a stateless Node.js container (Docker / Cloud Run / AWS ECS / Render / Fly.io).
- Default `HOST=0.0.0.0` ensures the container listens on external network interfaces across cloud PaaS providers.
- Build the backend before container execution via `npm run build:server`.
- Inject `GEMINI_API_KEY` through your host's secret management service. Never expose it in client builds.
- Configure `ALLOWED_ORIGIN` or `ALLOWED_ORIGINS` to match your deployed frontend origin(s) (e.g. `https://neorex-astra.web.app`). In production, unauthorized or missing origins are strictly rejected with HTTP 403.
- In split deployments (e.g. Vercel/Firebase Hosting for frontend and Cloud Run/Render for backend), set `VITE_DR_ASTRA_BACKEND_URL` on the frontend build environment to point to the backend domain. In unified/containerized deployments, leave it empty to use same-origin `/api/dr-astra/chat`.
- Node.js version constraint: Node.js >= 22.0.0 is strictly required by `@google/genai` package metadata engine specification.
